# Vesper development rules

- Before platform-specific work, select `platforms/README.md` and the explicit PC/Spark entry. Use separate checkouts and local bindings; run `python -m vesper.workspace check` before guarded progress, results or Spark probes. Do not silently rebind a mismatch or infer current progress from an unfiltered repository-wide search. Migrate a legacy PC checkout only in its own active task.
- Shared model code does not transfer qualification. Use the registry allowlist for progress reads/update packets and retain hardware/profile/source identity in results. Helper checks are workflow checks, not OS-level read isolation.

- Preserve the released model's weights, scales, activation quantization, KV rounding, routing and sampling semantics in the released-precision comparator. The PC operator now explicitly permits quality variation for useful speed/memory gains. Evaluate approximate candidates as separately named, opt-in numerical experiments with measured output quality, speed and memory; do not silently replace original assets or inherit exact-fidelity qualifications. Other platforms retain their own gates.
- The released-precision path requires the trained router correction bias. Extra quantization, expert pruning or changed routing/sampling must be declared in an experimental numerical profile and compared with the released comparator. A workspace execution profile such as `native` is not a numerical-precision profile.
- Use short representative checks and cached qualified references for routine development. Full per-layer/per-token tracing is for diagnostics or a deliberate qualification milestone, not a prerequisite for every performance experiment. Keep complete task prompts/budgets and report abbreviated probes as their own scope; do not mark deferred evaluations complete.
- For current PC planning, use `docs/quality-speed.md`, `docs/roadmap.md` and `docs/validation.md`. Historical evidence/reproduction documents qualify their recorded scopes; their old next steps do not define today's queue. Documentation-only changes need link/scope/evidence-preservation checks, not model replay. Optional mechanisms are conditional, not mandatory milestone gates merely because they were proposed.
- PC development repeats a bounded quality/speed improvement loop. Each changed candidate returns to the existing evaluation coverage; assess quality and speed together, improve unmet criteria, and revalidate earlier coverage before extending it. M2/#11 records a completed finite experiment, not permission to advance once into a separate quality-only stage. Choose coverage, order and acceptance explicitly; do not turn illustrative user examples into requirements. Declare an execution budget and save incomplete work instead of adding automatic retries, sweeps or long captures. A short raw-text run does not qualify an approximate profile's task quality.
- Use fixed subsets of selected public benchmarks during development. Prepare a concrete full-evaluation plan when a final candidate is ready, showing scope, subset results, estimated comparator/candidate time and uncertainty, resource impact and pause/resume support. The user decides whether to execute it; obtain explicit authorization for the presented plan before running either path on a full benchmark. Continue already authorized preparation and bounded subset work independently. An authorized full evaluation covers every item in each selected benchmark's declared split and measures degradation against a provenance-matched released-precision comparator. Preserve prompts/budgets/protocols; partial or deferred work is not a full-suite pass. Final-test failures return to the loop; further full evaluations need a user decision unless already covered by the approved plan. Do not invent benchmark selections or degradation thresholds.
- The selected PC loop entry is the fixed three-question GPQA Diamond development subset in docs/gpqa-subset.md. Complete its native execution readiness and collect real benchmark outputs; independent raw-text/component probes remain supplementary and must not replace benchmark quality or silently become the next primary task.
- Report format checks, specification checks, official-kernel parity, and full-model quality as separate results. Passing one does not prove the others.
- Keep host memory available for other work. The provisional full-engine cap is 96 GiB, with a 32 GiB system-available floor. Small probes have their own much smaller limits. Track pinned buffers and scratch as well as caches. A reservation counter is not proof of an OS-level memory limit.
- Do not stop other workloads, change the page file, reset GPUs, or download the full checkpoint as part of a small probe.
- Treat design proposals as hypotheses. Keep measured results and assumed performance ceilings distinct. Explain the evidence when revising a conclusion.
- Do not commit model weights, downloaded reference sources, local paths, credentials, GPU UUIDs, or machine names. Preserve third-party licenses for adapted code.
- Use English for public source documentation; maintain a short Japanese entry point. Keep status and unresolved validation gates honest.
- Track development in the repository's Issues and Milestones; see docs/roadmap.md. Link the active issue in commits and update its progress with scoped evidence. Use status:needs-validation for implemented work with an open required validation or quality check. Add verified and close only when the issue's stated acceptance checks pass; do not close a milestone for a component-only pass.
