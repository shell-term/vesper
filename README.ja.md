# Vesper（ヴェスパー）

GPU・RAM・SSDを組み合わせ、大きなMoEモデルをローカルPCで動かすための推論エンジンです。
最初のPC対象はDeepSeek-V4.1-Flash-1017、RTX 4090＋RTX 3080 Tiです。
公開済みの重みを使う設計なので、Vesperを使うための再学習は不要です。

[PC版の入口](platforms/pc-heterogeneous/README.md)・[DGX Spark版の入口](platforms/dgx-spark/README.md)
から対象を選びます。以下はPC版の記録で、Spark版の合格を示しません。

## 現在の方針

品質をできるだけ保ち、速度とメモリ使用量との釣り合いで実装を選びます。
速度向上に見合う品質の変化は許容し、追加圧縮や計算量の削減も実験候補に含めます。
目標は1会話の連続生成で20トークン/秒です。まだ未達成で、品質変化も合わせて測定します。

- 元の数値精度の経路を比較基準として残し、元の重みは変更しません。
- 近似を使う候補は別の設定名で、実際の出力品質・速度・メモリを比較します。
  全候補にビット単位の完全一致を要求する方針ではありません。
- 普段は短い検証と計測を使い、全層・全トークンの詳細照合は診断や必要な節目に絞ります。
- 採用する公開ベンチマークは開発中に固定した少数問を使い、最適化後の最終試験では全問を実行して元の精度からの劣化を測ります。
  初回は[GPQA Diamondの固定3問](docs/gpqa-subset.md)です。現在は入力準備・採点処理・実行可否の判定までで、モデルによる正答率は未評価です。
  評価対象と許容する劣化量は別に決め、最終試験で未達が出た場合も改善ループへ戻ります。
  全問評価の前に対象・少数問の結果・比較元を含む推定時間・資源使用量・中断再開の可否を提示し、実施するかはユーザーが判断します。
  提示した計画への明示的な承認後に開始し、保留した評価は未完了として残します。
- エンジンのRAM予約上限96GiB・システムの空き32GiBを初期条件として維持します。
  予約量と実際のRAM使用量は別に測ります。

元のexpert重みはすでに4bit形式です。追加圧縮の有効性も実測で判断します。
詳しくは[品質と速度の方針](docs/quality-speed.md)、[検証の選び方](docs/validation.md)を参照してください。
[改善項目の一覧](docs/pc-improvement-plan.md)に、実測した問題・改善案・採用前の確認を整理しています。
問題単位の保存・中断後の再開管理は実装しました。実モデルへ接続する経路は引き続き開発中です。

## できていることと限界

比較基準の部品・全40層の接続を検証し、短い自然文の生成と、Python式を答える課題1問を実行しました。
コード課題は34回の処理で `xs[-1]` と終了記号を生成し、宣言した3つの入力例すべてで正解しています。
[実行・状態復元の全記録](docs/trajectory-validation.md)を公開しています。

キャッシュを生成中に保持する短い試験では、生成速度が **0.0472→0.0762トークン/秒** になりました。
この入力の出力と最終状態は比較基準に一致し、RAM実測は約15.80GiB、空きは最小約117.74GiBでした。
予約上限が異なる1回ずつの試作測定で、実用速度にはまだ届いていません。
[計測条件・失敗した試行・全結果](docs/session-lifetime.md)も残しています。

その後のM2では、補助GPUの保存枠を同容量のRAMへ移す候補を、順番を入れ替えて2回ずつ比較しました。
短い入力での生成速度は合算で **0.07331→0.10972トークン/秒（約1.50倍）** になり、全回で出力・最終状態が基準に一致しました。
計測した4実行の処理時間合計は約8.4分です。[条件と採否判断](docs/m2-placement.md)を公開しています。
20トークン/秒は未達成で、長い入力や画像での速度・品質を示す結果ではありません。

一般的な品質、推論・ツール課題、任意の入力での実用速度は引き続き開発対象です。
途中で止めた推論課題は未完了・未採点で、長時間の詳細照合を自動再開しません。
3080 Tiは現在、重みの保管・整合性確認に使い、モデル計算は4090で行います。
新しい `host-retained` の試験経路はRAMへ退避し、モデル計算は同じく4090で行います。

画像入力も対応予定の要件として[Issue #26](https://github.com/shell-term/vesper/issues/26)に登録しています。
現状の入力処理は画像を拒否するため、画像の前処理・視覚エンコーダ・本文への接続と実画像での評価が別途必要です。

## 進め方

[PC用Issues](https://github.com/shell-term/vesper/issues?q=is%3Aissue+label%3Aplatform%3Apc-heterogeneous)
を進捗の正本とし、[ロードマップ](docs/roadmap.md)に節目の目的をまとめています。
開発は**精度・速度を測る→未達の原因を改善する→既存の評価に戻って確認する**ループで進めます。
評価範囲を広げて問題が見つかった場合も、改善後は以前の範囲へ戻って確認します。
具体的な入力・評価順・合格基準は別に決め、一度の合格を変更後の実装へ引き継ぎません。
完了済みのM0・M1とM2の実験は、それぞれの条件で得た比較基準・実績として残します。
M3の未完了評価もこのループ内で扱い、M2が閉じたことを理由に長時間の評価を自動で始めません。
各回の作業時間と計測予算を決め、未完了は保存して[区切りと停止条件](docs/roadmap.md#next-execution-order-and-time-limits)に従います。
過去の検証レポートの「次に行うこと」は当時の記録として区別します。

実行環境とCPU確認は[英語README](README.md#start)、部品の再現手順は[プローブ手順](docs/probes.md)、
個別の実績は[検証記録の索引](docs/reference-evidence.md)を参照してください。
これは研究段階の実装で、すぐに任意の会話を行う完成済みアプリではありません。
